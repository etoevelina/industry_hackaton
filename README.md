# Локальная система прокторинга — Integrity Score вместо надзора

Система отвечает не на вопрос «списывал или нет», а на вопрос **«насколько можно доверять
результату этого экзамена»** — и показывает, из чего это доверие сложилось. Защищённая
оболочка (Electron) держит рабочее окружение, Python-сайдкар смотрит в камеру и микрофон,
движок событий превращает шумные покадровые наблюдения в редкие обоснованные инциденты, а
fusion-слой связывает поведение студента с содержанием его ответов. На выходе — подписанный
HTML-отчёт с хеш-цепочкой, а вместе с ним — пакет `<сессия>.proctor.zip`: отчёт, журнал, кадры,
подпись и `manifest.json` со sha256 всех файлов одним файлом, который экзаменатор забирает и
проверяет одной командой. Решение по-прежнему принимает человек. Всё работает **полностью
локально**: ни один кадр, ни один сэмпл звука, ни один байт телеметрии не уходит в сеть.

Что отчёт и пакет **доказывают**: комплект после подписания не менялся, журнал связан хешами и
пересчитывается. Чего они **не доказывают**, пока приватный ключ лежит на машине экзамена: что
журнал собрала система, а не человек с правами администратора на этой машине. Это разные
утверждения, и `scripts/verify_report.py` печатает их отдельными строками — см.
[`docs/LIMITATIONS.md`](docs/LIMITATIONS.md), раздел 7.

## Быстрый старт — четыре команды

```bash
bash scripts/setup.sh      # .venv, зависимости сайдкара и оболочки, самопроверка
make models                # веса детектора объектов (однократно, единственный шаг с сетью)
make run                   # сайдкар + оболочка; Ctrl+C гасит оба процесса
make verify                # проверить подпись отчёта и хеш-цепочку доказательств
```

Нет камеры, моделей или времени — работает демо-режим по сценарию:

```bash
make run-mock              # мок-сайдкар гоняет scripts/demo_scenario.json, камера не нужна
make test                  # импорты, синтаксис JS, валидность сценария демо
```

Мок говорит по тому же протоколу и считает risk-score теми же весами — оболочка разницы
не видит. Это план Б на демо-день, см. [`docs/DEMO.md`](docs/DEMO.md).

Опциональные каналы ставятся отдельно и **не обязательны**:
`bash scripts/setup.sh --vision --audio --identity`. Отсутствие пакета выключает свой канал,
а не систему — см. [таблицу деградации](docs/ARCHITECTURE.md#4-деградация).

## Сверх ТЗ — семь вещей, которых в кейсе нет

| Что | Зачем это, какую дыру закрывает |
|---|---|
| **Fusion поведения и содержания** ([`engine/fusion.py`](sidecar/engine/fusion.py)) | Отвод взгляда сам по себе не доказывает ничего. Связка «взгляд ушёл на 5.2 с → через 1.1 с 312 символов со средним интервалом 11 мс при базовой скорости студента 170 мс» — доказывает. Закрывает главный вектор 2026 года: LLM на втором устройстве. **Приоритет не наш:** концепция известна и запатентована ProctorU (US11205349B2 — потеря лица или профильный ракурс на ~10 с, затем ввод с клавиатуры или мыши, затем отправка ответа; это дословно наше правило 1). Отличается реализация: персональная базовая линия набора **этого** студента внутри **этой** сессии, разложение вклада по каналам и полная локальность без сервера. |
| **Непрерывная верификация личности** ([`detectors/identity.py`](sidecar/detectors/identity.py)) | Обычный прокторинг проверяет лицо один раз на входе — дальше за клавиатуру может сесть кто угодно. Сверка эмбеддинга раз в 3 с, решение по скользящему окну. |
| **Анти-спуфинг (liveness)** | Фото перед камерой, зацикленное видео, подменённый поток: отсутствие морганий, статичность области лица, детект повтора последовательности кадров. Работает даже без insightface — на одном numpy. |
| **Проверки окружения** ([`env_checks.py`](sidecar/env_checks.py)) | Виртуальная камера (OBS/ManyCam/Droidcam/EpocCam), ПО удалённого доступа, виртуальная машина, запись экрана, чёрный список процессов, второй монитор. Это второй, независимый от камеры источник доказательств: подмену видеопотока в кадре не увидеть принципиально. |
| **Аудио-канал** ([`detectors/audio.py`](sidecar/detectors/audio.py)) | Главный признак — не распознавание голоса, а рассинхрон: речь в микрофоне есть, губы сомкнуты (`SPEECH_WITHOUT_LIP_MOTION`). Так выглядит подсказка через наушник. Звук на диск не пишется никогда. В шумном компьютерном классе канал даёт ложные срабатывания на соседей, поэтому выключается одним флагом (`make run ARGS="-- --no-audio"`) — см. [`LIMITATIONS.md`](docs/LIMITATIONS.md#3-ограничения-моделей-где-возможны-ошибки-и-что-с-ними-сделано). |
| **Подписанный tamper-evident отчёт** ([`storage/db.py`](sidecar/storage/db.py), [`storage/report.py`](sidecar/storage/report.py)) | `hash_n = sha256(prev_hash ‖ canonical_json(body_n))`, genesis выводится из метаданных сессии, отчёт подписан Ed25519. Правка одного байта рвёт цепочку, `make verify` показывает номер записи. Отчёт перестаёт быть картинкой и становится доказательством. Подпись при этом имеет **честную семантику** из трёх состояний: `self_signed` (ключ на машине экзамена) — доказательство только целостности при передаче; `institution` **без сверки эталона** — ровно та же сила, потому что метку ставит тот же процесс, который собрал пакет; `institution` **со сверенным эталоном** (`--trusted-pub`) — «у процесса был доступ к ключу вуза». `authority_info(authority, verified)` в [`storage/handover.py`](sidecar/storage/handover.py). Мы не пишем «отчёт подлинный» там, где это неправда. |
| **Эскалация без автоматического приговора** ([`engine/risk.py`](sidecar/engine/risk.py)) | 30 баллов — мягкая подсказка в HUD, 60 — автоматическая пауза с возможностью вернуться в рамку, 90 — порог «нужно решение преподавателя»: экзамен остановлен, но снять остановку или аннулировать работу может только человек. Студент всегда видит, что именно зафиксировано; risk-score затухает (half-life 90 с), поэтому случайная ошибка на второй минуте не клеймит до конца теста; разложение по видам событий даёт преподавателю не «риск 64», а «телефон ×2 +41, взгляд вниз ×3 +18». <br>**Как это держится в коде:** `cap_auto_action()` в [`sidecar/protocol.py`](sidecar/protocol.py) опускает любое автоматическое `LOCK` до `AUTO_ACTION_CAP = PAUSE`; на пороге 90 `_apply_action()` открывает запрос решения (событие `LOCK_REVIEW_REQUESTED` плюс запись `control`/`lock_review_requested` в хеш-цепочке) и приостанавливает сессию; спад риска приостановку не снимает ни в сайдкаре, ни в оболочке (поле `review_required` вердикта); снять её или подтвердить блокировку могут только команды `proctor_lock` / `proctor_release`, обе — с обязательным полем `actor`. Исключение одно и объявленное: флаг `--auto-lock` возвращает автоматическую блокировку, и тогда это видно в `policy_info()`, в HUD и в отчёте. |

## Разведка источников LMS — откуда берётся белый список

Профиль экзамена разрешает перечисленные источники и блокирует остальное. При внедрении
выясняется, что списка **не знает никто**: Moodle тянет свой домен, но рядом оказываются CDN,
шрифты, видеосервер, счётчик и иногда поставщик единого входа. Список, написанный руками,
означает сорванный экзамен на незагрузившемся скрипте. Список «с запасом» (вроде `edu.kz`
целиком) открывает половину интернета — ядро такую запись и не примет.

Поэтому список не придумывается, а **собирается наблюдением**:

```
make discover URL=https://lms.вуз.edu.kz/login/index.php
# или: scripts/discover-origins.command https://lms.вуз.edu.kz/login/index.php
```

Открывается обычное окно, в котором человек проходит путь студента (вход → курс → тест).
Фильтр запросов в этом режиме **ничего не блокирует** — только записывает: источник, тип
ресурса и страницу, которая его попросила. Кнопка «Вход завершён» (`Cmd+Shift+L`) делит
найденное на фазу входа (`auth_origins`) и фазу экзамена (`exam_origins`) — заготовка под
двухфазный белый список, который ядро пока не умеет. На выходе — **черновик** профиля, где у
каждой записи стоит строка «нужен потому что: `<страница>` запросила `<ресурс>`».

Главное правило инструмента — **не опознал, значит не включил**. В `allowed_origins` черновика
попадают ровно три вещи: адрес экзамена, соседи по домену вуза и именованный список CDN, **на
который нельзя положить свой файл** (шрифты Google, cdnjs, раздачи jQuery и Bootstrap). Всё
остальное, что страница запрашивала, уходит в раздел `candidates` — с объяснением, что именно
через источник открывается, и готовой строкой для вставки руками.

Разворот сделан по итогам ревью, и вот его цена в обе стороны. Прежняя версия включала
незнакомый хост «с пометкой решает человек», и в белый список уезжали `pastebin.com`,
`dropbox.com`, `web.whatsapp.com` и `cdn.jsdelivr.net` — последний по схеме
`/gh/<юзер>/<репо>@<ветка>/<файл>` отдаёт **любой** файл из **любого** публичного репозитория
GitHub, то есть студент за минуту публикует шпаргалку и читает её с «нужного CDN». Сверка с
ядром от этого не защищает: ядро знает три класса отказа (поисковик, ИИ-ассистент, зона
целиком), и файлообменник для него — обычный `ok`. Теперь ошибка стоит другого: у студента не
загрузится виджет, а проктор добавит одну строку, прочитав, что она открывает.

Четыре вещи, которые делают это инструментом настройки, а не второй системой правил:

- **Правила общие.** Разбор записей, опознание поисковиков и класс «зона целиком» берутся из
  [`shell/state.js`](shell/state.js) — того самого слоя, который работает на экзамене. Вторых
  правил нет.
- **Сверка с ядром — вызовом ядра.** Вопрос «а эта запись вообще подействует?» задаётся
  `classify_origin()` из [`sidecar/config.py`](sidecar/config.py) отдельным процессом
  ([`tools/discover/core_check.py`](tools/discover/core_check.py)), а не угадывается копией
  таблиц. Всё, что ядро отклонит, из черновика уходит с причиной. Граница этой сверки названа
  в самом выводе: «примет» значит «запись подействует», а не «через неё нельзя списать».
- **Черновик нельзя применить молча.** `issued_by` и `issued_at` остаются заглушками, а в
  `notes` стоит метка `ЧЕРНОВИК-НЕ-УТВЕРЖДЁН`. Ядро ищет и то, и другое: пока они на месте,
  `exam_ready` равен `false`, причина попадает в шапку отчёта, и в подписанном документе
  остаётся след, что правила собрала программа. Снимается барьер одним осознанным действием —
  проктор вписывает своё имя и дату.
- **Прогоны накапливаются, а не затирают друг друга.** Полнота набирается несколькими
  проходами, поэтому второй прогон в тот же `--out` **дополняет** первый: вычеркнутое руками
  не возвращается никогда, заполненные поля проктора не перетираются, прошлый файл
  откладывается копией `*.bak.json`.

Отдельно — **единый вход**. Если среди найденного оказывается `login.microsoftonline.com`,
`accounts.google.com`, Okta, Keycloak, свой `idp.` или просто `login.вуз.edu.kz`, инструмент не
включает его в черновик и говорит прямым текстом: разрешив такой источник, вы открываете не
«вход», а весь аккаунт — для Microsoft это Outlook, Teams и OneDrive одним и тем же живым
сеансом. Правильный путь другой: студент входит в LMS **до** старта экзамена, и поставщик в
белый список не попадает вовсе.

И отдельно — **чего разведка не видела**. Это второй раздел вывода, до списка, а не после, и
он целиком едет в файл: длительность прогона, число запросов, число открытых страниц, какие
типы ресурсов не встретились ни разу (нет ни одного встроенного кадра — значит встроенные
тесты не проверялись), какие адреса страница **предлагает** студенту ссылками и формами, и
какие адреса лежат **в тексте её скриптов**, ни разу не запрошенные. Последнее нашло на LMS
заказчика настоящий случай, описанный ниже.

### Внедрение в вузе — профиль за минуту

```
make discover URL=https://lms.вуз.edu.kz/login/index.php ARGS="--out exam-profile.json"
```

1. **Пройдите путь студента** в открывшемся окне: вход → курс → тест → загрузка файла. После
   входа нажмите «Вход завершён» (`Cmd+Shift+L`), в конце — «Сохранить черновик» (`Cmd+S`).
2. **Прочитайте первый экран разбора.** Там написано, чего разведка не видела. Если стоит
   «открыта ВСЕГО ОДНА страница» или «ни одного встроенного кадра» — прогон неполон, идите по
   курсу ещё раз **тем же** `--out`: прогоны накапливаются.
3. **Пройдите раздел КАНДИДАТЫ.** У каждой записи сказано, что через неё открывается, и готова
   строка для вставки. Добавляйте только то, без чего у студента ломается страница.
4. **Вычеркните лишнее** из `allowed_origins`. Вычеркнутое инструмент больше не вернёт.
5. **Впишите себя**: `issued_by`, `issued_at`, `institution`, `exam_id` — и уберите метку
   `ЧЕРНОВИК-НЕ-УТВЕРЖДЁН` из `notes`. До этого момента сайдкар не считает экзамен готовым.
6. **Проверьте на себе**: запустите экзамен с `--exam-profile <файл>` и пройдите тест. Всё,
   что фильтр не пустил, лежит в журнале с полным адресом — по нему и видно, чего не хватило.

Что инструмент **не гарантирует** — отдельным документом: [`docs/LIMITATIONS.md`](docs/LIMITATIONS.md),
раздел «Разведка источников LMS».

### Боевая проверка на LMS заказчика

Astana IT University, только страница входа, без логина. `curl` видит обычную форму Moodle и
одну внешнюю ссылку на `moodle.com` в подвале. Живая разведка за 42 секунды собрала 39
запросов, нашла 2 источника и показала то, чего `curl` не видел:

- в черновик попал **один** хост — `lms.astanait.edu.kz`;
- `ps1-dev.oes.kz` ушёл в кандидаты как «назначение не опознано» (это сторонний скрипт
  `inject.php`, подключённый к странице входа);
- и главное — **в тексте этого скрипта** нашлись `aitu.oes.kz` и `ajax.googleapis.com`, ни
  разу не запрошенные. Скрипт **спящий**: на странице входа он молчит, а просыпается по
  `#isExam` и уходит на `aitu.oes.kz`. Это собственный прокторинг вуза, и профиль, собранный
  «по странице входа», заблокировал бы его: сорванный экзамен плюс ложный инцидент в журнале.
  Чтение тел скриптов — единственное, что находит такое до экзамена.

Чтобы тело скрипта отдавалось целиком, запрос делается по **полному** адресу: по обрезанному
`inject.php` сервер отдаёт заглушку в 4.8 КБ без единого адреса, а по
`inject.php?site2=lms.astanait.edu.kz` — 19 КБ с обоими хостами. Полный адрес живёт только в
памяти процесса: в файл и на экран он не попадает никогда, потому что в строке запроса Moodle
носит `sesskey`, а поставщики входа — одноразовые коды.

Слой правил проверяется 192 проверками на чистом node: `node tools/discover/check.js`.
Барьер против неутверждённого черновика — в `make test`, разделом «Профиль экзамена».

## Чем это отличается от коммерческого прокторинга

Сравнение с публичными описаниями Proctorio, ProctorU, Respondus, Examity, Honorlock и Safe
Exam Browser. Сначала то, где мы объективно слабее, — чтобы остальное читалось как инженерия,
а не как маркетинг.

**Чего у нас нет и не будет за девять дней:** измеренной точности на десятках тысяч видео,
когортной нормировки «списала вся группа», внедрения в полторы тысячи вузов. Мы не заменяем
коммерческий прокторинг. Мы показываем, что локальная система без отправки данных наружу
даёт преподавателю достаточно фактов для решения.

Три отличия, каждое проверяемо в коде, а не в презентации:

| Отличие | Что у нас | Чем это отличается от рынка |
|---|---|---|
| **Взгляд в координатах экрана** | калибровка по 9 точкам, два полинома 2-й степени по `[1, u, v, u², uv, v²]` дают `screen_x`/`screen_y`; качество калибровки считается **LOO-кросс-валидацией** (`good_rmse 0.08`, `fair_rmse 0.16`, грейд `poor` с просьбой переснять), пороги — 3 робастные сигмы от `1.4826·MAD`. Мы различаем «смотрит в правый край своего монитора» (x≈0.95) и «смотрит на устройство справа» (x>1.3) | Proctorio публично заявляет, что **не отслеживает движения глаз**, и работает на детекции лица «отвёл взгляд на продолжительное время». У Respondus есть нормировка на глобальный корпус и на когорту, но персональной карты экрана в описании нет. На детекции лица край своего монитора и устройство рядом неразличимы в принципе |
| **Потолок у привычки** | четыре вида отведения взгляда и поворот головы — **один кластер** с потолком: `штраф = база × min(1 + 0.6·(√(масса/база) − 1), 4)`. Порядка 120 отведений взгляда дают integrity **77–81** независимо от того, как они распределены по видам: привычка смотреть на клавиатуру физически не может опустить вердикт ниже третьего уровня из четырёх | у Proctorio веса метрик задаются относительно друг друга, а сами метрики считаются независимо и складываются по видам — шкала зависит от номенклатуры детектора, и достаточно размножить виды, чтобы опустить студента. Такой защиты от накопления однотипных срабатываний мы у вендоров не нашли |
| **Честная семантика подписи** | три состояния, не два: `self_signed` — ключ на машине экзамена, подпись доказывает **только целостность при передаче**, и в отчёте так и написано; `institution` **без сверки эталона** — то же самое, потому что метку ставит тот же процесс, который собрал пакет; `institution` **со сверенным эталоном** — «у процесса был доступ к ключу вуза». `verify_report.py` возвращает 0 только в третьем случае | вендоры из разобранных либо держат ключ на сервере и не проговаривают, что именно доказывает подпись, либо не подписывают отчёт вовсе. Разделения «целостность / авторство» нет ни у одного |

О происхождении fusion-связки: концепция запатентована ProctorU (US11205349B2) и известна
с 2021 года, приоритет не наш — см. строку про fusion в таблице выше.

## Приватность

Это система прокторинга, а не слежки. Что именно происходит с данными:

**Что пишется на диск**
- `sessions/<ts>_<student_id>/evidence.sqlite` — журнал инцидентов: вид, время, длительность,
  уверенность, числовые детали, русская формулировка. Каждая запись связана хешем с предыдущей.
- `sessions/<ts>_<student_id>/evidence/` — кадры и 15-секундные клипы **только вокруг
  подтверждённых инцидентов**. Кроп делается по боксу предмета-повода. Отдельные кропы лиц
  не сохраняются; для `SECOND_FACE` и `IDENTITY_MISMATCH` доказательством служит полный кадр,
  а лица посторонних на нём размываются. Для `SECOND_FACE` клип не пишется вовсе: размыть
  движущегося постороннего в видео нечем, и биометрия человека, который на экзамен не
  подписывался, на диск не попадает.
- `report.html` + `report.html.sig` + `report.html.pub` — отчёт, подпись, публичный ключ.

**Что не пишется никогда**
- Видео целиком. Кадры живут только в оперативном кольцевом буфере (несколько секунд) и
  затираются при закрытии.
- Звук. Ни wav, ни «временные файлы для отладки»: сэмплы существуют только в ОЗУ, наружу
  уходят лишь производные признаки (флаг речи, RMS, близость к профилю голоса).
  Распознавание слов не делается и не предусмотрено.
- Нажатые клавиши и текст ответов. Телеметрия для fusion — это межклавишный интервал в
  миллисекундах, класс клавиши (`char`/`nav`/`ctrl`) и длина вставки. Символы не покидают
  renderer. Кейлоггер в системе прокторинга невозможно защитить, и мы его не делали.
- Эталон лица и профиль голоса. Это векторы признаков, а не изображения и записи, и до
  диска они не доходят вообще: живут в памяти процесса сайдкара и исчезают вместе с ним.
  В каталоге сессии их нет, восстановить по ним исходные данные нельзя.

**Где это лежит и куда не уходит**
- Всё внутри репозитория: `sessions/`, `evidence/`, `keys/`. Эти каталоги в `.gitignore`.
- Сетевых обращений наружу нет ни одного. Единственный канал — WebSocket на `127.0.0.1:8787`
  между двумя локальными процессами. Единственный шаг, которому нужен интернет, —
  однократная подготовка весов `make models` до экзамена.
- Студент видит в HUD всё, что фиксируется: активные каналы, текущий risk-score, список
  инцидентов с формулировками. Скрытого режима нет.

Этика, минимизация данных и право студента — [`docs/LIMITATIONS.md`](docs/LIMITATIONS.md#этика-и-приватность).

### Как экзаменатор получает доказательства

По завершении сессии рядом с её каталогом собирается **пакет** —
`<сессия>.proctor.zip`: отчёт с подписью и публичным ключом, `evidence.sqlite`,
кадры, метаданные и `manifest.json` со sha256 всех файлов. Манифест подписан тем
же ключом, поэтому подписанный манифест закрывает весь пакет сразу. Куда писать
сессии, задаётся при запуске:

```bash
python3 sidecar/main.py --sessions-dir /Volumes/exam-share/qih   # шара вуза или USB
PROCTOR_SESSIONS_DIR=/Volumes/exam-share/qih python3 sidecar/main.py
```

Каталог проверяется на запись **до** начала сессии, пробной записью. Недоступен —
сессия пишется в запасной локальный каталог, и это помечается как
`degraded_handover` в отчёте и в пакете, а не замалчивается.

### Проверка пакета

`scripts/verify_report.py` принимает пакет, каталог сессии или один файл отчёта:

```bash
python3 scripts/verify_report.py <сессия>.proctor.zip
python3 scripts/verify_report.py sessions/<сессия>
python3 scripts/verify_report.py sessions/<сессия>/report.html
make verify                                                 # последняя сессия
python3 scripts/verify_report.py <пакет> --trusted-pub university.pub
```

Коды возврата: `0` — комплект, цепочка и сверка ключа с эталоном сошлись;
`1` — обнаружено расхождение; `2` — подделки не найдено, но проверка **неполная**
(в том числе `self_signed` и `institution` без эталона: целостность подтверждена,
авторство — нет).

Про эталон ключа, и это важнее, чем выглядит. `report.html.pub` едет вместе с
отчётом, поэтому сам по себе ничего не доказывает: кто пересоберёт отчёт и
подпишет своим ключом, получит согласованную пару «отчёт + подпись». Метка
`institution` этого не меняет — её ставит тот же процесс, который собрал пакет.
Эталоном может быть **только файл, который проверяющий хранит сам**:
`--trusted-pub`. Эталона по умолчанию нет; `keys/report_ed25519.key.pub` на
машине проверяющего эталоном не является, и сравнение с ним объявляло подделкой
честные пакеты. Полное решение — приватный ключ у вуза и подпись на сервисе
экзамена: см. `docs/LIMITATIONS.md`, разделы 4A и 7.
